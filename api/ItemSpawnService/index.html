ItemSpawnService

Turns a rolled loot table into stacks that actually go somewhere.

ItemSpawnData decides WHAT spawns and owns no items. This decides what that becomes: it resolves each ItemSet's ClassName through ItemService, builds an ItemStack, and places it -- nesting included, so a crate can spawn with a backpack in it that has things in the backpack.

WHAT CHANGED

spawnItemFromItemSet constructed an item object per set, called SetQuantity and SetDurability on it, and recursed into parent_item.InventoryManager:AddItem(child_item). Three things went wrong there and are gone here:

  • SetQuantity clamps to the stack limit and destroys at zero, so a spawn table asking for more than a stack silently produced less and never said so. Fill returns what did not fit.
  • a child whose parent had no InventoryManager warned and then added it anyway, to nil. Nesting is explicit now and reports where it failed.
  • an unknown ClassName warned per occurrence, every respawn, forever. Unresolved sets come back in the result instead.

DURABILITY IS A PERCENTAGE

ItemSet.Durability is 0-100 and is multiplied by the item's own MaxDurability. The original did that multiplication two functions away from where the field was set, which is a good way to read it as absolute.

ToStack​

ItemSpawnService:ToStack(item_set: ItemSet) → ItemStack?

Build one stack from one rolled set.

Returns nil when the ClassName does not resolve. Durability is applied as a percentage of the item's own maximum; a set that names no durability gets the item's default.

Flatten a rolled tree into stacks, losing the nesting.

For callers that only want "what items did this produce" -- a preview, a drop table, ContainerService.SpawnProvider. Use Fill when the nesting matters.

Place a rolled tree into an inventory, building nested inventories as needed.

Returns what was placed and what was not, with a reason -- the original warned and carried on, so a loot table that had drifted out of date kept spawning less than it claimed with nothing but console noise to show for it.

Nesting has to attach to a holder, and TransferToGroup does not say which one it filled. Searching for the class afterwards is unambiguous in practice because a nested spawn is a container item and containers do not stack.

ProviderFor​

</>
ItemSpawnService:ProviderFor(
spawn_data: SpawnData,
options: RollOptions?
) → (any) → {ItemStack}

A ContainerService.SpawnProvider bound to a spawn table.

The provider contract is flat -- it hands back stacks and lets the container place them -- so nesting is lost through this path. A container whose loot includes containers should be filled with Spawn directly.

OwnedProvider​

</>
ItemSpawnService:OwnedProvider(options: RollOptions?) → (any) → {ItemStack}

A provider for owners that carry their OWN spawn table.

ProviderFor binds one table for every caller, which suits a container type whose loot is fixed. A ground spawner is the other case: each one references different spawn data, so the provider has to read it off the owner.

Works for anything shaped { SpawnData, State = { Randomness } }, which is both GroundSpawnerData and ContainerData. An owner with no spawn data yields nothing rather than erroring -- an unconfigured spawner is a normal state, not a fault.
