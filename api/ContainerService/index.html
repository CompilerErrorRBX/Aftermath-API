ContainerService

World containers: crates, lockers, vehicle storage, loot piles.

WHAT CHANGED

A container's contents were a bespoke InventoryController reached through container.Inventory, and opening one reached all the way into client.Manager.AccessibleInventoryManager to attach it -- so the service that owns crates also owned a piece of the replication protocol, and could not be exercised without a live client session.

Here a container's contents are an ordinary Inventory of kind Container, and Open RETURNS the inventories to expose rather than attaching them. Who receives them is the replication layer's business. That inversion is what lets open/close/search/lock be tested with no player, no network and no place.

ItemGroup containers -- the ones whose slots hold items that are themselves containers, like a pile of backpacks -- were the messiest part of that coupling: opening one walked every slot, found each item's nested inventories, and attached them individually with Silent metadata, then re-ran the same walk on every slot change. InventoryService already tracks nesting by holder id, so that walk is CollectInventories and the change handling is one signal.

WHAT IS DELEGATED

Loot spawning still belongs to ItemSpawnDataService, which is not ported. SpawnProvider is the seam it will plug into; until then SpawnItems reports that it spawned nothing, which is exactly what an unconfigured container should do. Sounds and attribute writes live in the binding.

Put quantity from holder into the container.

The mirror of Take, and the reason a drop pile works: a container is just an inventory, so depositing is the same transfer in the other direction.

CollectInventories​

</>
ContainerService:CollectInventories(container: ContainerData) → {Inventory}

Every inventory a viewer of this container should be able to see.

For an Inventory container that is just its own. For an ItemGroup it is its own plus the inventory nested inside each slot -- a pile of backpacks shows the backpacks' contents, not the backpacks.

The old version did this walk inline in OpenContainer, and again in a slot-change handler, and again in CloseContainer to undo it. Nesting is tracked by holder id now, so it is one function with one caller per event.

Open​

</>
ContainerService:Open(
container: ContainerData,
player: Player
) → {Inventory}?

Open the container for a player.

Returns the inventories to expose, or nil when the open was refused -- disabled, locked, or out of range. Note what it does NOT do: attach anything to the player. OnContainerOpened plus this return value is the whole protocol, so the replication layer decides what reaches the client.

Close​

</>
ContainerService:Close(
container: ContainerData,
player: Player
) → {Inventory}

Close the container for a player.

Safe to call for a player that never had it open -- the old version had to run its listener cleanup in that case anyway, because a vanished client left connections behind. There are no per-viewer connections now, so there is nothing to leak.
