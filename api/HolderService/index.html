HolderService

Operations over ItemHolders.

Every mutating function here is CONSERVATIVE: the total quantity across all holders involved is identical before and after. Nothing is destroyed as a consequence of arithmetic. A holder that reaches zero becomes empty and stays a holder -- removing a ground pile from the world is a separate, explicit decision, not a side effect of the last item being taken.

Contrast the current path, where BaseItem:SetQuantity clamps to the stack limit, discards the difference, and calls self:Destroy() at zero.

Functions​

CreateGround​

</>
HolderService:CreateGround(stack: ItemStack?) → ItemHolder

A world pile.

Gets a bare CUID: a ground pile has no owner, so there is nothing to derive an id from. Unlimited by default -- the ground has no stack limit.

CreateSlot​

</>
HolderService:CreateSlot(
owner_id: string,
slot_key: string | number,
max_quantity: number?,
accepts: ((config: ItemConfig) → boolean)?
) → ItemHolder

A slot inside something.

The id is DERIVED: {owner_id}_{slot_key}. For an inventory the key is the slot's allocation index; for equipment it is the equip type, which reads straight off the wire (aB3f_Primary). Either way the id is reproducible from facts both realms already have, so replicating a slot costs the key rather than an opaque string.

max_quantity nil means unlimited -- that is the replacement for threading unlimited_stack through every call.

LimitFor​

</>
HolderService:LimitFor(
holder: ItemHolder,
config: ItemConfig
) → number?

The stack limit that actually applies to config in this holder.

nil means unbounded. Holder override first, then the item's own MaxQuantity -- so an item definition still sets the default stack size and a container can raise or lower it. Shared with TransactionService, which needs the identical rule against the projected state.

Transfer​

</>
HolderService:Transfer(
from: ItemHolder,
to: ItemHolder,
quantity: number?,
group: HolderGroup?
) → TransferResult

Move up to quantity from one holder to another.

Returns what moved and what did not. THE REMAINDER STAYS IN from -- that is the whole point. Picking up a 5,000 pile into 200 units of space leaves 4,800 on the ground rather than deleting them.

group is the destination's weight context, if it has one.

TransferToGroup​

</>
HolderService:TransferToGroup(
from: ItemHolder,
group: HolderGroup,
quantity: number?
) → TransferResult

Move a stack into the first holders that will take it, in order.

This is the pickup path: try each slot, keep whatever will not fit in the source. Returns the total moved.

Split​

) → ItemStack?

Take quantity out as a free-standing stack.

Used for drag-and-drop and for dropping to the world: the caller owns the returned stack and must place it somewhere. Returns nil if nothing moved, never a zero-quantity stack.
