GroundItemService

World piles, as holders.

WHAT CHANGED

The old service ran a parallel item lifecycle beside the inventory one. A ground spawn owned an Item object, subscribed to its OnUpdate signal, and mirrored quantity and durability onto a part attribute from inside that callback. Dropping had three branches -- merge into a nearby pile, clone the item for a partial drop, or move the whole object and clear the slot it came from -- and each branch had to decide for itself whether the source slot was now empty.

A ground pile is already an ItemHolder with Unlimited capacity, so all three branches are one Transfer. Conservation is the transfer's job: whatever does not fit stays in the source holder, because the source holder still exists. Nothing is cloned, nothing is destroyed to make an arithmetic result come out, and no slot has to be cleared as a side effect -- an emptied holder is simply an empty holder.

What is left here is the part the model does not cover: where a pile sits in the world, which cell it hashes to, and which part instance represents it.

TESTABILITY

World and Schedule are injectable seams, the same pattern ItemContextService uses for Schedule and HasPermission. Both default to doing nothing, so every function below runs headless -- no workspace, no part pool, no raycast. The Roblox-side implementation is installed at boot by GroundItemBinding, which is the only piece that needs a running place.

NO SESSION OBJECT

Range checks take a Player and resolve the character through CharacterUtil, which goes to CustomCharacter's PlayerList -- Player.Character is NOT the authority in this game. Read fresh rather than cached, unlike the client.PrimaryPart it replaces, which went stale across a respawn. See the convention note in src2/PORT.md.

FindMergeable​

stack: ItemStack,
position: Vector3
) → GroundSpawn?

A pile in the same cell that stack could merge into.

Merge eligibility is HolderService:AreMergeable, which compares durability and skin as well as class. The old service compared ClassName alone and additionally refused to merge anything whose MaxQuantity was 1, so a damaged rifle could absorb a pristine one. This is stricter, and it is the rule the rest of the model already uses -- see the merge-strictness open question in src2/PORT.md.

Drop​

</>
GroundItemService:Drop(
holder: ItemHolder,
cframe: CFrame,
quantity: number?,
options: DropOptions?
) → GroundSpawn?

Drop quantity out of holder onto the ground.

holder is wherever the quantity is coming from -- an inventory slot, an equipment slot, another pile. It is NOT emptied unless the whole stack moves, and it is never cleared as a side effect: an emptied slot is just an empty slot, and the caller does not have to know which of those happened.

Returns the pile the quantity landed in, which may be one that already existed.

Take​

</>
GroundItemService:Take(
spawn: GroundSpawn,
inventory: Inventory,
quantity: number?
) → TransferResult

Move quantity from a pile into an inventory.

Returns what actually moved. A pile that empties is removed; one that does not is left exactly as it is, holding the remainder -- which is the case the old model could not express, because the thing holding the excess was the item being taken.

Take, gated on the player being close enough.

Remove​

</>
GroundItemService:Remove(spawn: GroundSpawn) → ItemHolder

Take a pile out of the world.

The stack it holds is NOT destroyed -- the holder is handed back, so a caller that is moving a pile somewhere else keeps what was in it. Piles that expire or are cleared simply drop the reference, which is what destruction means for data that owns no identity.
