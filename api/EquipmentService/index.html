EquipmentService

Equipment slots, built on ItemHolder.

Replaces Inventory/EquipmentController.luau. (Which, note, does not currently compile: it opens with seven const declarations, and const is not Luau.)

WHAT CHANGES

An equip slot IS an ItemHolder -- capacity 1, plus an Accepts predicate that encodes "can this item go in this slot". So equipment, inventory slots and ground piles are finally the same type, and a move between them is HolderService.Transfer with no special case.

Three behaviours are deliberately different from the old controller:

  • Equip RETURNS what it displaced rather than disposing of it. The old one unequipped, then task.deferred an AddItem-or-else-Drop; if the inventory was full and Drop failed, the item was simply gone, and because the work was deferred the caller could not tell. Here the displaced stack comes back and placing it is the caller's decision -- the same rule the rest of Inventory2 follows.

  • Slots are created for the declared EquipmentTypes and nothing else. GetEquipmentSlot used to lazily create a slot for ANY string, so a typo produced a real, permanently empty slot that Serialize would then walk.

  • Nothing is validated after a mutation. Swap checked compatibility, then mutated, then fired signals; here the checks all happen first, so a refused swap cannot leave one side moved.

ResolveEquipType​

</>
EquipmentService:ResolveEquipType(
equipment: Equipment,
config: ItemConfig,
preferred: EquipmentType?,
first_open: boolean?
) → EquipmentType?

Which slot this item should go in.

  • preferred wins when the item allows it,
  • first_open then falls back to the first ALLOWED type whose slot is free,
  • otherwise the item's own declared type.

Pure -- it reads the equipment but changes nothing, so a caller can ask "where would this land" without committing to it. The old Equip inlined this logic after it had already begun mutating.

Equip​

Put a stack into an equip slot.

Returns what was displaced. Nothing is dropped, deleted or deferred -- if the caller ignores Displaced, the stack is leaked to the garbage collector, not silently destroyed inside a task.defer the way it used to be.

Unequip​

</>
EquipmentService:Unequip(
equipment: Equipment,
equip_type: string
) → ItemStack?

Take whatever is in a slot back out, and hand it to the caller.

The old Unequip decided for itself: task.defer an AddItem, and Drop if that failed. Both of those are placement decisions the caller is better placed to make -- and doing them deferred meant a failure surfaced nowhere.

Swap​

</>
EquipmentService:Swap(
equipment: Equipment,
from_type: string,
to_type: string
) → boolean

Exchange two equip slots.

Refuses unless BOTH occupants may live in the other's slot. Every check runs before the first write, so a refusal cannot leave one side moved -- the old Swap had three separate mutate-then-fire branches, one of which fired OnUpdate and two of which did not.

Clear​

</>
EquipmentService:Clear(equipment: Equipment) → {ItemStack}

Empties every slot and returns the contents.

Handed back rather than destroyed: tearing down a loadout is not a reason to delete a player's gear. The old Clear spawned an item:Unequip per item on a separate thread and returned the items anyway, so callers raced it.
