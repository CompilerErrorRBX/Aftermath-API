TransactionService

Staged inventory changes: build up a set of moves, then commit them all or throw them all away. Entirely optional -- the direct HolderService / InventoryService calls still work and are unchanged.

WHY

Multi-step operations today mutate as they go, so a failure halfway leaves the inventory in a state no caller asked for: a craft that consumes three ingredients and cannot place the output has already eaten the ingredients, and a trade that moves five stacks and stalls on the sixth has moved five.

HOW

A transaction keeps a copy-on-write SHADOW of every holder it touches. Staged operations read and write the shadow, never the real holders, so nothing is visible until Commit. Drop discards the shadow and the world is untouched -- there is no rollback step to get wrong, because nothing moved.

VALIDITY

Each staged operation is validated against the PROJECTED state, not the current one. Stage two 100-round adds into a single 100-round slot and the second fails immediately, because by then the projection already shows the slot full. So the projected state is valid at every step, and committing it cannot produce a state the rules would have rejected.

CONCURRENCY

The baseline quantity of every touched holder is recorded when it is first shadowed. Commit re-checks it: if anything moved underneath the transaction -- another commit, a direct call, a pickup on another thread -- the commit is refused rather than clobbering the newer value.

Applies every shadow at once.

Refuses when the transaction is invalid, already resolved, or when a touched holder changed underneath it. Returns false without applying anything -- partial application is exactly what this exists to prevent.

Drop​

</>

Discards the transaction. Nothing was ever applied, so there is nothing to undo -- this only releases the shadow.

Stage a move between two holders.
