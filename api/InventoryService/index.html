InventoryService

Inventories, containers and the world, built on HolderService.

HolderService knows how to move quantity between two holders safely. This layer knows what holders MEAN: which inventory they belong to, which of them own nested inventories, and how weight rolls up through nesting.

Every mutating operation still preserves the conservation invariant -- nothing here destroys a stack to make the numbers work.

GetNetworkSerialized​

</>
InventoryService:GetNetworkSerialized(inventory: Inventory) → Types.NetworkInventory

Wire payload for one inventory. See Types.NetworkInventory for why the shape lives there rather than in the route module.

THREE ARRAYS, NOT ONE RECORD PER SLOT

Slots every live slot number, in order. Position in this array is the slot's position, and the client derives its id as {Id}_{Number}. Sending the numbers -- rather than a count -- is what makes slot add/remove replicable, since numbers are never reused and so have gaps. LimitOverrides only slots whose limit differs from SlotLimit. Contents only slots that hold something.

One record per slot was the obvious shape and the wrong one: BufferNet spends a whole byte on every Optional presence flag, so a 30-slot bag with 10 items spent ~210 bytes saying "empty" 20 times over. Splitting the arrays roughly halves the payload without touching the transport.

NOT REPRESENTED: a holder's Accepts predicate. It is a function, so no wire format can carry it -- the client has to reconstruct slot filters from the inventory's own definition.

GetNetworkSubtree​

</>
InventoryService:GetNetworkSubtree(inventory: Inventory) → {Types.NetworkInventory}

An inventory and everything nested beneath it, parents first.

BufferNet structures cannot recurse, so a container's contents travel as their own snapshot; this is what a caller sends together to make the tree complete.
