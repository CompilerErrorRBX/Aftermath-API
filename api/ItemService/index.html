ItemService

Owns item registries and every operation over ItemInstance records.

Replaces the class-level state that lived on BaseItem: Item.Items -> instances_by_id Item.ItemsByUId -> instances_by_uid Item.CIDMap -> class_id_to_name (still exposed for the client auth payload) Item.UIdSignals -> uid_waiters items_by_class_name/class_names/class_by_class_id -> configs / sorted_class_names

Allocation, per instance: old: table + its own metatable + Destroy closure + OnUpdate Event (+ _SlotChangeEvents table, + OnSlotChange Event when touched) new: one table. Change notification is a small set of service-level signals carrying the item, rather than an Event allocated per item.

Functions​

Register​

</>
ItemService:Register(list: {ItemConfig}) → ()

Registers item kinds and assigns class ids.

Class ids must match on client and server (they index the CIDMap the client receives as auth data), so they are derived from a sort of every registered ClassName -- same rule as BaseItem:ModuleLoad, but computed once over the whole set instead of re-sorted on every module load.

CreateComponent​

</>
ItemService:CreateComponent(
defaults: {[string]: any},
derive: ((config: {[string]: any}) → ())?
) → Component<Fields,Overrides,Config>

Builds a config constructor for one item category.

defaults are shared by reference across every item built from this component -- configs are treated as immutable after registration, so a table default (Tags, Stats) is deliberately not deep-copied.

RegisterFolder​

</>
ItemService:RegisterFolder(container: Instance) → ()

Requires every ModuleScript under container and registers what they return.

Keeps the drop-a-file-in-and-it-registers property of the old *.item wildcard, but as an ordinary folder walk against a typed registry rather than a global name registry. The returned value is unchecked (it is a dynamic require), so a malformed item file surfaces at registration rather than at analysis -- the item FILES are fully checked by their component.

ResolveClassName​

</>
ItemService:ResolveClassName(class_name: string) → (
string,
string?
)

Maps a ClassName that may be deprecated onto the one that still exists, plus the skin the old item becomes.

Saves hold ClassNames, and 175 of them name items that were retired -- each had a DeprecationConfig saying "I am now , wearing ". Those modules are gone; DeprecatedItems.luau carries the same mapping as data. Returns the input unchanged when it is not deprecated.

Note the skin is NOT always derivable from the name: BunnyBackpack.item maps to skin 'EasterBunnyBackpack'. 45 of the 175 differ that way.
